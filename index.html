Security flow

Frontend authorization is driven by effective permissions, not role names.

This document captures the frontend-observable security flow in this repo. The backend may enforce extra rules, but the frontend models visibility and access through the current profile's flattened permission set.

Route access Menu visibility Button visibility Profile permissions

Frontend Authorization Lens

The signed-in profile is loaded from /users/me.

ProfileService.profile() stores the flattened permissionIds.

PermissionService checks those ids for routes, menus, buttons, and sections.

Effective flow

Effective Flow

Assigned Roles

Application-scoped permission bundles attached to the user.

Assigned UserGroups

Company-scoped groups whose permissions also contribute to the user.

Flattened Permission IDs

The backend returns the effective union, and the frontend uses that final set.

The current frontend flow is effectively user <- roles + usergroups. Direct user-permission assignment exists in the API type, but no direct assignment UI was found in this frontend.

Important Nuances

Where things live

Only role and permission are under top-level /security. User and usergroup are managed inside /management/company/:companyId/....

app.routes.ts:317 / company-detail.component.ts:90

Assignment authority

Target user type changes the required assignment permission. Root or system-company users require ADMIN_MANAGER.ASSIGN_*; customer users require CUSTOMER_MANAGER.ASSIGN_*.

permission.constant.ts:42 / user-detail-dialog.component.ts:167

Check semantics

The guard and directive infrastructure supports all, but checks found in this repo are effectively OR-based through hasAnyPermission unless explicitly overridden.
